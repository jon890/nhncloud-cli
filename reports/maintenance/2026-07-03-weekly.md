## 발견 항목

### P0

- 없음.

### P1

#### 1. 숫자 옵션 파싱 규칙이 명령마다 다르다

- 근거:
  - `src/commands/instance/images.ts:25`와 `src/commands/instance/flavors.ts:20`은 `Number(value)`로 정수 옵션을 파싱한다.
  - `src/commands/instance/create.ts:112`, `src/commands/instance/create.ts:128`, `src/commands/instance/create.ts:131`은 `parseInt`를 사용한다.
  - `src/commands/logncrash/search.ts:54`, `src/commands/logncrash/search.ts:55`도 `parseInt`를 사용한다.
  - 반면 `src/commands/volume/list.ts:20`, `src/commands/deploy/binaries.ts:33`, `src/commands/deploy/upload.ts:37`, `src/commands/deploy/download.ts:30`은 별도 helper에서 `Number(value)`를 쓰되 정규식 검증을 함께 둔다.
- 중요한 이유:
  - `parseInt("10abc", 10)`처럼 뒤에 쓰레기 문자열이 붙은 값이 통과할 수 있다.
  - `Number(value)` 기반 검증은 지수 표기나 공백 입력을 허용할 수 있어 명령마다 사용자 경험이 달라진다.
  - NKS 구현에서 노드 수, 업그레이드 버퍼 수, 인증서 기간 같은 숫자 옵션이 추가되므로 지금 기준을 고정하면 새 명령의 편차를 줄일 수 있다.
- 제안 행동:
  - `src/commands` 공용 위치에 `parseIntegerOption` 계열 helper를 추가하거나, 이미 검증이 탄탄한 명령의 패턴을 승격한다.
  - 우선 `instance create`, `instance images`, `instance flavors`, `logncrash search`, `deploy run`만 한 작업으로 묶는다.
- 검증:
  - 각 대상 명령의 parser 단위 테스트를 추가한다.
  - `1e2`, `10abc`, 빈 문자열, 공백, 음수, 0 허용 여부를 명령별 정책으로 고정한다.
  - `pnpm tsc --noEmit`와 관련 command help smoke 검증을 실행한다.
- 실행 경로: `build-with-teams`

### P2

#### 1. IaaS 계열 클라이언트 resolver 흐름이 세 곳에서 반복된다

- 근거:
  - `src/commands/instance/helpers.ts:13`부터 `src/commands/instance/helpers.ts:20`
  - `src/commands/network/helpers.ts:14`부터 `src/commands/network/helpers.ts:21`
  - `src/commands/volume/helpers.ts:14`부터 `src/commands/volume/helpers.ts:21`
- 중요한 이유:
  - 세 helper 모두 profile 해석, IaaS 자격증명 로드, region override, Keystone 토큰 발급, 서비스별 client 생성을 반복한다.
  - NKS가 추가되면 같은 형태가 네 번째로 생길 가능성이 높다.
- 제안 행동:
  - 지금은 바로 추상화하지 않는다.
  - NKS Phase 1이 실제로 들어온 뒤 `nksEndpoint`와 기존 `computeEndpoint`/`networkEndpoint`/`blockStorageEndpoint` 차이를 보고 작은 factory를 검토한다.
- 검증:
  - 추상화 시 각 서비스 helper의 기존 반환 타입과 에러 메시지가 유지되는지 단위 테스트로 고정한다.
- 실행 경로: 보류 후 `ai-slop-cleaner` 또는 `build-with-teams`

### Defer

#### 1. 서비스 응답 guard 공통화는 아직 미룬다

- 근거:
  - `src/services/*/client.ts`에는 서비스별 응답 guard가 많다.
  - 이 저장소는 NHN 공통 봉투, Harbor REST, OpenStack 평면 JSON이 섞여 있다.
- 중요한 이유:
  - 응답 모델이 다른 서비스를 무리하게 일반화하면 ADR-006, ADR-017, ADR-019의 경계를 흐릴 수 있다.
- 제안 행동:
  - NKS 구현 중 `unwrap` 금지와 평면 JSON 처리가 실제로 추가된 뒤, 반복된 guard만 좁게 추출할지 다시 판단한다.
- 검증:
  - 각 서비스의 fixture 기반 client test가 먼저 있어야 한다.
- 실행 경로: 조치 없음
