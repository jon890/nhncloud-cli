# 0005 — 이름 지정 팀원의 회신이 team-lead 에 도착하지 않았다

- plan: 065-feat-deploy-appkey-profile
- 상태: 우회

## 무슨 일이 있었나

`name` 을 지정해 스폰한 팀원 둘이 작업은 정상으로 마쳤는데 회신이 team-lead 에 닿지 않았다.

- `critic-p065` — 22분 대기, 재요청 1회, 그래도 무응답
- `executor-p01` — 구현을 정상으로 마쳤고 파일 변경도 남겼는데 완료 보고가 오지 않았다

두 경우 모두 `~/.claude/teams/session-*/inboxes/team-lead.json` 이 계속 빈 배열이었다.
팀원 인박스도 비어 있었다 — team-lead 가 보낸 지시는 소비됐다.
그래서 team-lead → 팀원 방향은 살아 있고 반대 방향만 끊긴 상태였다.

## 왜 일어났나

원인은 확정하지 못했다. 확정한 것은 방향성 하나다.
같은 세션에서 **이름 없는 subagent 는 정상으로 결과를 반환했다.**
그 경로는 최종 응답 텍스트를 도구 결과로 되돌려주므로 팀 인박스를 지나지 않는다.

## 무엇을 했나

두 팀원을 다르게 다뤘다.

- critic 은 이름 없는 subagent 로 다시 돌렸다. 평가 3회(REVISE 2회 포함)를 그 경로로 끝냈다.
  프롬프트에 "SendMessage 를 쓰지 말고 최종 텍스트로 보고해라" 를 명시했다.
- executor 는 산출물이 이미 worktree 에 있었으므로 재실행하지 않았다.
  team-lead 가 phase 본문의 통과 조건을 직접 실행해 완료를 확인했다.

## 다음에 할 것

이름 지정 스폰은 여전히 1순위다. 협업 사이클을 이어가는 이점이 크다.
다만 **첫 회신이 오지 않을 때의 판단 시점을 앞당긴다.**

- 팀원에게 착수를 지시한 뒤 회신이 없으면 한 번 재요청한다. 여기까지는 기존 절차와 같다.
- 재요청에도 무응답이면 **팀 인박스 두 개를 직접 확인한다.**
  `~/.claude/teams/session-*/inboxes/{team-lead,<팀원>}.json` 이 모두 비어 있으면 회신 경로 문제다.
  팀원이 아직 생각 중인 것과 구분된다.
- 회신 경로 문제로 판정되면 팀원 종류에 따라 갈린다.
  - 판정을 받는 역할(critic·code-reviewer·docs-verifier)은 이름 없는 subagent 로 다시 돌린다.
    판정이 산출물이라 회신이 끊기면 아무것도 남지 않는다.
  - 구현하는 역할(executor)은 재실행하지 않는다. 산출물이 worktree 에 남아 있으므로
    team-lead 가 phase 의 통과 조건을 직접 돌려 완료를 확인하는 편이 싸다.
- 어느 팀원을 왜 폴백으로 내렸는지 실행 보고에 남긴다.

폴백으로 내려가면 잃는 것이 있다. 이름 없는 경로는 재요청마다 컨텍스트를 처음부터 다시 쌓는다.
이번 critic 재평가에서 team-lead 가 직전 판정과 반영 라인을 매번 프롬프트에 다시 담아야 했던 이유가 그것이다.
