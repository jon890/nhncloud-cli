**증상**: 기존 동작을 **반대로** 바꾸는 변경인데, 계획이 그 자리의 기존 로직을 "그대로 쓰라" 고 지시한다.
기존 로직은 옛 목표에 맞게 만들어져 있어 새 목표에서 중립이 아니라 대체로 반대로 작동한다.

plan063 에서 두 번 나왔다. `export` 를 "실패하면 안 남긴다" 에서 "실패해도 남긴다" 로 뒤집는 변경이었다.

- "기존 close 대기 로직으로 stream 을 닫는다" — 그 로직은 `stream.destroy()` 였고, destroy 는 버퍼에 남은 write 를 **버린다**. 지우는 것이 목표였을 때는 맞았다. 보존이 목표가 된 뒤 그대로 쓰니 부분 파일이 빈 파일로 나왔다.
- "정렬이 `logTime DESC` 이므로 마지막 값이 가장 오래된 시각" — 창 분할 루프가 창을 **오래된 쪽부터** 처리해서 정렬 방향과 순회 방향이 어긋났다. 그 값으로 이어받게 하면 미조회 구간이 빠진다.

**Good**:
- 목표를 뒤집는 변경에서 기존 로직 재사용을 지시할 때, 그 로직이 **옛 목표를 위해 무엇을 하는지** 한 줄로 적는다. 적을 수 없으면 확인하지 않은 것이다.
- 이름이 아니라 동작으로 인용한다. "close 대기 로직" 은 이름만으로는 재사용해도 될 것처럼 보인다.
- 정렬·순서를 근거로 지점을 고를 때는 **정렬 규칙과 순회 순서를 함께** 확인한다. 둘이 다른 축일 수 있다.

**검출**:

```bash
# cwd: <repo root>
# 실패 경로를 바꾸는 phase 에서 기존 함수를 그대로 쓰라고 한 곳
grep -n "기존 .*로직\|그대로 쓴다\|그대로 유지한다\|재사용한다" tasks/<plan>/phase-*.md
# 각 대상 함수를 열어 옛 목표를 위해 무엇을 하는지 확인
```

**Self-check**: 이 변경이 기존 동작을 반대로 만드는가?
그렇다면 재사용하라고 지시한 로직이 옛 목표를 위해 무엇을 하는지 적었는가?
순서를 근거로 삼은 곳에서 정렬 축과 순회 축이 같은가?

**Why**: plan063 에서 이 패턴이 데이터 손실 두 건으로 이어질 뻔했다.
하나는 critic 이 계획 단계에서, 하나는 executor 가 구현 중 테스트 실패로 잡았다.
계획을 쓴 쪽은 둘 다 놓쳤다 — 자기가 세운 전제는 다시 읽어도 전제로 보인다.
