**증상**: phase 본문이 "이 실패는 위험하지 않다" 는 **판단 근거**를 적어놓고, 그 사실을 사용자에게 알리라는 **지시**는 적지 않는다.
구현자는 지시가 아닌 문장을 구현하지 않으며 그 판단은 옳다.
결과적으로 되돌릴 수 없는 작업이 실패로 보고되고, 사용자는 아무 일도 없었다고 읽고 재실행한다.

정상 경로의 안내는 문구를 따옴표로 못박으면서 실패 경로는 "이유" 만 적고 넘어가는 편향이 있다.

**Good**: 되돌릴 수 없는 호출(배포·삭제·전송)이 있는 phase 는 실패 경로마다 셋을 함께 지시한다.

- 코드가 낼 문구 — 따옴표 안에 그대로
- 그 출력을 고정하는 테스트 — 나오는 경우와 나오지 않는 경우 양방향
- 사용자가 읽는 문서에 옮기라는 지시 — 공개 스킬 참조·README

실패 상태를 한 종류로 뭉치지 않는다. "서버가 결과를 알려준 실패" 와 "결과를 모르는 실패" 는 사용자가 할 일이 반대다.
전자는 원인을 고쳐 재실행이고 후자는 재실행 금지다. 한 문구로 덮으면 자동화가 어느 쪽을 따를지 갈린다.

**검출**: grep 으로 잡기 어렵다 — 문구가 **없다**는 것을 셀 수 없다. 계획 작성 시 self-check 로 다룬다.

```bash
# cwd: <repo root>
# 되돌릴 수 없는 호출이 있는 명령 파일에서, 실패 경로 안내가 있는지 눈으로 확인할 대상만 추린다
grep -rln "requireYes" src/commands/ | xargs grep -Ln "process.stderr.write"
```

**Self-check**: 이 phase 에 되돌릴 수 없는 호출이 있는가?
그 호출이 성공한 뒤 실패하는 경로가 있는가(대기 타임아웃·후속 조회 오류)?
그 경로에서 사용자에게 낼 문구를 따옴표로 못박았는가?
그 문구가 나오는 경우와 나오지 않는 경우를 테스트로 고정했는가?
그 문구를 공개 문서에 옮기라고 지시했는가?

**Why**: PR #91 (plan054-3) — `apigateway stage deploy create` 가 배포 접수 뒤 대기 타임아웃으로 끝나면
명령은 실패로 보고하는데 배포는 서버에 남아 있었다. phase 본문에 "대기가 끊겨도 배포는 취소되지 않는다" 고
적혀 있었으나 그것은 폴링 오류를 전파해도 되는 이유였지 사용자에게 알리라는 지시가 아니었다.
같은 phase 가 `import-resources` 와 `rollback` 의 안내는 문구까지 못박았다.
code-reviewer 가 MAJOR 로 잡았고, 교정 뒤에도 `FAILURE` 확정 경우에 반대 지시가 나가는 것을 다시 잡았으며,
docs-verifier 가 그 교정이 공개 문서에 옮겨지지 않은 것을 또 잡았다. 세 단계에서 같은 간극이 반복됐다.
