# ADR-034: Log & Crash export 완료 결과 보존

- **결정**: `logncrash export`는 조회 중 실패와 조회 완료 뒤 로컬 파일 실패를 서로 다른 결과 상태로 다룬다.
  - 조회 중 실패는 [[adr-032]]에 따라 `<output>.partial`로 보존한다.
    API 재조회가 필요한 상태이며 이어받는 방법을 안내한다.
  - 모든 데이터를 받고 파일 형식까지 완성했지만 최종 교체에 실패하면 `<output>.<id>.complete`로 보존한다.
    그대로 사용할 수 있으며 API 재조회가 필요 없다.
  - 모든 데이터를 받았지만 JSON 배열 닫기에 실패하면 `<output>.<id>.unfinalized`로 보존한다.
    API 재조회는 필요 없지만 배열 닫기를 확인해야 한다.
  - `<id>`는 실행별 고유값이다.
    복구 파일은 앞선 실행 결과를 덮어쓰지 않으며, 이후 실행이 성공해도 자동 삭제하지 않는다.
  - 최종 교체가 끝난 뒤에만 성공을 표시한다.
    완료 뒤 로컬 파일 오류는 원인과 복구 경로를 stderr에 알리고 `EXIT_PARAM_ERROR`로 끝낸다.
  - 복구 파일 이동도 실패하면 임시 파일을 삭제하지 않고 그 경로를 알린다.
- **맥락**: 기존 구현은 모든 창과 페이지를 받은 뒤 `rename`이 실패하면 임시 파일을 삭제했다.
  대량 조회에 쓴 호출 비용과 전체 결과가 함께 사라져 사용자는 같은 API를 다시 호출해야 했다.
  JSON 배열 닫기 실패는 조회 중 실패 처리에 들어가 완전한 데이터가 `.partial`로 분류되고 이어받기 안내까지 나갔다.
  두 경로 모두 API 수집 상태와 로컬 파일 상태를 하나의 성공 또는 실패로만 나눈 데서 생겼다.
  조회가 끝났는지, 파일 형식이 완성됐는지, 최종 경로 교체가 끝났는지를 따로 구분해야 사용자가 필요한 복구 작업을 정확히 선택할 수 있다.
- **대안 기각**:
  - 완료 결과를 계속 삭제하기 — 드문 로컬 오류 한 번으로 비싼 원격 조회를 다시 수행해야 한다.
  - 두 실패를 모두 `.partial`로 보존하기 — API 재조회 필요 여부를 구분하지 못하고 완전한 데이터를 다시 받게 한다.
  - 고정된 `.complete`와 `.unfinalized` 경로를 사용하기 — 새 실패가 앞선 복구 결과를 덮어쓸 수 있다.
  - JSON 배열을 자동으로 고치기 — 쓰기 실패 원인을 모르는 상태에서 형식이 완전하다고 단정할 수 없다.
  - 자동 재실행을 추가하기 — 로컬 파일 실패에 API 재호출은 필요 없으며 이 결정의 범위를 벗어난다.
- **트레이드오프**: 사용자가 확인할 때까지 복구 파일이 남으므로 저장 공간을 직접 관리해야 한다.
  대신 CLI가 서로 다른 실행 결과를 추측해 삭제하지 않는다.
- **적용 범위**: 이 ADR은 `logncrash export`가 API 조회를 마친 뒤 처리하는 파일 상태와 사용자 안내에 한정한다.
  [[adr-032]]의 조회 중 실패와 `.partial` 이어받기 규칙은 바꾸지 않는다.
