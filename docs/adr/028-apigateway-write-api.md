# ADR-028: API Gateway 쓰기 API — 플러그인 upsert, 필수 필드 보존, 하위 일괄 적용

- **결정**: 스테이지 수정과 리소스 플러그인 설정을 서버 시맨틱에 맞춰 얇게 감싸고,
  CLI 가 플러그인 목록을 재구성하지 않는다.
  - 플러그인 변경은 경로(`resource-paths`)와 메서드(`resource-methods`)를 분리한 두 명령으로 노출한다.
    설정 가능한 플러그인 타입이 경로는 4종, 메서드는 5종으로 다르다.
  - 요청 본문은 API 형식 그대로 JSON 파일로 받는다.
    공식 문서의 요청 예시를 그대로 옮겨 쓸 수 있게 하려는 것이다.
  - 서버가 upsert 이므로 기존 플러그인을 읽어 병합하지 않는다.
    보낸 타입만 추가·변경되고 나머지는 그대로 남는다.
  - 값의 의미와 무관하게 필수인 필드(`backendEndpointUrl`·`methodName`)는 기존 값을 조회해 채운다.
  - 하위 경로·메서드 일괄 적용은 CLI 순회가 아니라 `applyChildPath` 로 서버에 맡긴다.
  - 쓰기 응답에는 조회용 타입 가드를 재사용하지 않는다.
- **맥락**: 같은 플러그인 목록이 위치마다 다른 이름으로 오간다.
  조회 응답은 `resourcePluginList`, 경로 요청은 `pathPluginList`, 메서드 요청은 `methodPluginList` 다.
  하나의 헬퍼로 이름을 공유할 수 없다.
  - `backendEndpointUrl` 이 필수라서 설명만 바꾸려는 호출도 기존 URL 을 실어야 한다.
    스테이지 단건 조회 경로가 없어([[adr-027]]) 목록을 받아 `stageId` 로 골라야 한다.
  - `methodName` 도 필수다. 플러그인만 붙이려는 호출이 이름을 빠뜨리면 기존 이름이 덮인다.
  - 스테이지 수정 응답에는 `stageCustomUrl` 과 `stageAliasDomainList` 가 없다.
    조회 응답에는 실측으로 두 필드가 있었다.
    조회 가드를 그대로 쓰면 API 가 성공했는데도 CLI 가 실패로 보고한다.
  - `applyChildPath` 는 하위 경로와 메서드 전체에 번진다.
    `delete` 와 함께 참으로 주면 하위 전체에서 그 플러그인이 사라진다.
  - CORS 플러그인은 하위에 OPTIONS 메서드를 자동으로 만들고 기존 OPTIONS 를 삭제·대체한다.
    플러그인 하나를 붙이는 호출이 다른 메서드를 지우는 유일한 경로다.
- **대안 기각**:
  - CLI 가 리소스를 순회해 하나씩 호출 — 실측 서비스가 68건이라 호출이 68회로 늘고,
    중간에 실패하면 절반만 적용된 상태가 남는다.
    `applyChildPath` 는 서버가 한 번에 처리한다.
  - 기존 플러그인을 읽어 목록 전체를 재구성해 전송 — upsert 라 불필요하다.
    읽고 보내는 사이에 콘솔에서 바뀐 설정을 덮어쓰는 위험만 늘어난다.
  - 설정값을 인라인 문자열 옵션으로 받기 — 설정에 `${request.path.appKey}` 처럼
    셸이 확장하는 문자열이 들어간다.
    따옴표를 틀리면 값이 조용히 비어 잘못된 설정이 그대로 적용된다.
  - 조회용 `isStage` 재사용 — 수정 응답에 없는 두 필드를 필수로 요구해 성공 응답을 거부한다.
- **트레이드오프**: `--dry-run` 이 보여주는 영향 범위는 `path` 접두 비교로 계산한 추정값이다.
  서버의 하위 판정과 완전히 일치한다고 보장할 수 없어, 출력에 추정임을 함께 알린다.
- **적용 범위**: 이 ADR 은 스테이지 수정과 리소스 플러그인 설정에 한정한다.
  변경한 리소스를 스테이지로 가져오는 반영과 배포·롤백은 별도 결정으로 남긴다.
