# ADR-026: HTTP 요청 타임아웃 전역 제어

- **결정**: 요청 타임아웃 기본값을 `api/timeout.ts` 한 곳에 두고 전역 옵션 `--request-timeout <sec>` 과 `NHNCLOUD_REQUEST_TIMEOUT` 환경변수로 대체할 수 있게 한다.
  - 기본 30초, 허용 범위 1~3600초. 우선순위는 옵션 > 환경변수 > 기본값이며 미지정 시 동작은 종전과 같다.
  - deploy 의 장시간 상한(600초)은 `max(전역 값, 600초)` 로 **커지기만** 한다. 전역 값을 낮춰도 바이너리 업로드·다운로드가 끊기지 않는다.
  - 값은 `export let` 으로 두고 각 service client 가 그 식별자를 참조한다. 요청 옵션은 호출 시점에 평가되므로 갱신이 그대로 반영되고, 요청 지점을 고치지 않는다.
  - 타임아웃으로 실패하면 오류 메시지에 현재 상한과 조정 방법을 함께 노출한다.
- **맥락**: [[adr-002]] 는 timeout·retry 정책을 한 곳에서 통일한다고 정했으나, 실제로는 같은 상수가 service client 10곳에 각각 선언돼 있었다.
  - 그중 logncrash 만 선언이 빠져 ky 기본값 10초로 동작했고, 기간이 넓은 검색이 10초에서 끊겼다(GitHub 이슈 #67). 같은 클라이언트를 쓰는 export 는 응답이 빨라 증상이 드러나지 않아 원인 추적이 늦었다.
  - 흩어진 상수는 한 곳이 빠져도 드러나지 않는다. 사용자에게는 상한을 조절할 수단이 없어 자동화에서 회피가 불가능했다.
- **대안 기각**:
  - 명령별 `--timeout` 옵션 — `instance create` 와 `ncs workload create` 가 이미 그 이름을 상태 폴링 대기 시간으로 쓴다. 한 이름이 두 의미가 되어 `--wait --timeout` 조합의 해석이 갈린다.
  - 대량 조회 명령에만 옵션 추가 — 옵션이 있는 명령과 없는 명령이 갈려, 이번 이슈를 만든 것과 같은 종류의 비대칭을 다시 만든다.
  - client 생성자로 주입 — 생성자 10개와 팩토리 10개를 바꿔야 하고 요청 74곳까지 값 전달 경로가 늘어난다. 얻는 것은 요청별 차등인데 그 요구가 없다.
  - 전역 값이 600초 상한까지 대체 — `--request-timeout 5` 같은 입력이 큰 파일 업로드를 끊는다. 낮추는 방향은 이득 없이 파괴적이다.
- **트레이드오프**: 전역 단일 값이라 한 명령 안에서 요청마다 다른 상한을 줄 수 없다. 상태 폴링 대기(`--timeout`)와는 별개 축으로 남으며 서로 대체하지 않는다.
