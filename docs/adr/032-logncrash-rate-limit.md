# ADR-032: Log & Crash 조회 횟수 제한 처리

- **결정**: rate limit 을 응답 봉투로 식별하고, 자동 재시도 없이 즉시 실패로 끝내되 받은 결과는 남긴다.
  - 판별은 봉투의 `resultCode` 로만 한다. HTTP 상태로 판정하지 않는다.
  - 백오프와 자동 재시도를 넣지 않는다. 429 는 즉시 실패로 끝낸다.
  - `export` 가 중간에 끊기면 받은 만큼을 `<output>.partial` 에 남기고 위치와 이어받는 방법을 알린다.
    `--output` 경로는 건드리지 않는다.
  - `--format json` 이면 부분 파일도 배열을 닫아 그대로 파싱되게 만든다.
  - 안내에서 기간을 좁히라는 유도를 뺀다.
- **대체된 부분**: 잔량 조회에 의존하지 않고 회복 속도를 안내에 쓰지 않는 결정은 [[adr-036]]이 대체한다.
  자동 재시도 배제와 429 부분 결과 보존은 그대로 유지한다.
- **맥락**: rate limit 은 HTTP 429 가 아니라 200 에 봉투 실패로 온다.
  - v3 공개 명세는 `search`·`scroll`·`scroll/{scrollKey}`·`cursor` 네 경로에 429 를 선언한다.
    그런데 실제 응답의 상태 코드는 200 이고 429 는 봉투 안에만 있다.
    HTTP 상태로 판정하는 코드는 이 응답을 성공으로 읽는다.
  - 응답 헤더에 `Retry-After` 도 `X-RateLimit-*` 도 없다. 실측으로 확인했다.
    얼마나 기다려야 풀리는지 서버가 알려주지 않는다.
  - 2026년 8월 31일에 10초 간격으로 관측한 회복량은 매번 16이었고, 60초 간격에서도 100이었다.
    공식 문서가 보장하는 속도는 아니며 [[adr-036]]의 추정 안내에만 사용한다.
  - 호출 비용은 조회 기간이나 쿼리 선택성 중 하나만으로 예측할 수 없다.
    앞선 실측에서는 `*`의 1시간과 6시간 창이 각각 약 1,034와 1,183이었고,
    `logSource`와 `logLevel`로 좁힌 쿼리는 호출당 약 85였다.
    후속 24시간 창 단일 호출에서는 같은 방식으로 좁힌 쿼리에 약 21,870이 관측됐다.
  - 기간을 좁히면 한 호출의 비용이 줄 수 있지만 호출 수가 늘어난다.
    공식 산정식이 없으므로 기간 분할을 rate limit 회복 방법으로 안내하지 않는다.
    이슈 [#91](https://github.com/jon890/nhncloud-cli/issues/91)에서는 6시간 창 28개 중 앞 6개만 성공했다.
  - 정확한 산정 규칙은 공식 문서에도 명세에도 없다. 위 값은 한 프로젝트의 측정이지 계약이 아니다.
    성공한 호출 하나가 현재 잔량보다 많이 차감돼 잔량이 음수가 될 수 있다.
    거부된 호출도 차감된다는 초기 해석은 산술을 다시 대조해 철회했다.
  - [[adr-030]] 의 적응형 분할은 500 에 대한 대응이며 그대로 유효하다.
    다만 분할이 호출 수를 늘려 rate limit 을 앞당길 수 있다. 429 를 만나면 분할하지 않고 멈춘다.
- **대안 기각**:
  - 백오프 자동 재시도 — 호출 비용을 사전에 알 수 없어 고정 간격으로 기다려도 다음 호출이 가능한지 보장할 수 없다.
    긴 시간 프로세스를 붙잡는 동작은 자동화에도 맞지 않는다.
  - 부분 결과를 `--output` 에 쓰기 — 잘린 파일과 완전한 파일이 구분되지 않는다.
    자동화가 불완전한 데이터를 전체로 오인한다.
  - 429 를 500 과 같은 안내로 묶기 — 기간을 좁히라는 유도가 rate limit 에서는 상황을 악화시킨다.
- **트레이드오프**: 실제 요청 직전의 동시 소비로 429를 만나면 사용자가 직접 다시 실행해야 한다.
  부분 파일이 있어 재실행 비용은 줄지만 자동으로 이어지지는 않는다.
- **적용 범위**: 이 ADR 은 `logncrash search` 와 `export` 의 rate limit 처리에 한정한다.
  `search` 의 500 원인은 다루지 않는다.
  이슈 [#91](https://github.com/jon890/nhncloud-cli/issues/91) 이 rate limit 으로 지목했으나 실측하면 별개다.
  다른 서비스의 봉투 오류 처리도 바꾸지 않는다.
