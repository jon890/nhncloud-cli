# ADR-030: Log & Crash 검색 기간 상한은 고정값이 아니다 — export 적응형 분할과 추정 안내

- **결정**: 검색 기간 상한을 상수로 두지 않고, `export` 가 500 을 만나면 기간을 절반으로 줄여
  다시 시도하는 방식으로 다룬다.
  - 성공한 창 크기를 기억해 나머지 구간에 그대로 적용한다. 매번 탐색하지 않는다.
  - 최소 창은 10분이다. 그 아래에서도 실패하면 분할을 멈추고 오류로 끝낸다.
  - 일부 창이 실패하면 파일을 남기지 않는다. 기존 `export` 의 부분 파일 방지 정책을 따른다.
  - `search` 는 분할하지 않는다. 500 을 받으면 원인을 단정하지 않는 안내와 서버 `requestId` 를 보여 준다.
  - 문서가 정한 90일·31일 사전 검증([[adr-024]] 전환 이전부터의 계약)은 그대로 둔다.
- **맥락**: 공식 API 가이드는 "최근 90일 이내" 와 "범위 31일 초과 불가" 만 정의하고
  그보다 짧은 상한은 어디에도 없다. v3 공개 명세에는 시간 제약 자체가 없다.
  - 실측하면 두 프로젝트의 실패 경계가 크게 다르다.
    한 프로젝트는 10일이 성공하고 14일이 500 이며, 다른 프로젝트는 6시간이 성공하고 12시간이 500 이다.
    40배 넘는 차이라 시간만으로 상한을 정할 수 없다.
  - 문서가 서술한 검색 토큰 차감은 원인이 아니다.
    잔량이 최대치(40000)인 상태에서도 500 이 났고, 실패한 호출은 토큰을 차감하지도 않았다.
  - 서버는 날짜만 준 값(`2026-08-03`)을 받지 않는다.
    `check request body. invalid datetime format 'from'` 과 함께 `resultCode: 400` 이 온다.
    그래서 `resolveTime` 이 그 형식을 통과시키면 CLI 검증만 지나고 서버에서 실패한다.
  - 500 응답 본문에는 `status`·`error`·`requestId` 만 있고 원인을 가리키는 필드가 없다.
    그래서 CLI 는 그 500 이 기간 때문인지 다른 이유인지 확정할 수 없다.
  - 문서의 31일 상한은 이 계정에서 도달할 수 없는 값이다. 14일에서 이미 실패한다.
    사전 검증만 남겨 두면 사용자는 통과한 요청이 서버에서 죽는 경험을 계속하게 된다.
- **대안 기각**:
  - 고정 상한 상수(예: 6시간)로 사전 거부 — 프로젝트마다 경계가 달라 한쪽에서는 통과할 요청을
    막고 다른 쪽에서는 여전히 500 이 난다. 관측된 두 경계의 차이가 40배다.
  - 토큰 잔량으로 사전 판정 — 잔량이 가득할 때도 실패해 판정 근거가 되지 못한다.
  - 500 을 기간 초과로 단정해 안내 — 근거가 없다.
    서버가 원인을 주지 않으므로 다른 원인일 때 사용자를 잘못된 방향으로 보낸다.
  - `search` 도 분할 — `--cursor` 로 페이지를 이어 가는 계약([[adr-024]])과 충돌한다.
    창마다 커서가 따로 생겨 사용자에게 무엇을 돌려줄지 정할 수 없다.
- **트레이드오프**: 적응형이라 실패 호출이 몇 번 섞인다.
  전체 기간으로 한 번 시도해 보고 줄이는 구조라, 로그가 많은 프로젝트일수록 첫 몇 번이 헛돈다.
  성공 크기를 재사용해 그 비용을 한 번으로 묶는다.
- **적용 범위**: 이 ADR 은 `logncrash export` 의 기간 분할과 `search` 의 500 안내에 한정한다.
  날짜만 준 시각 입력을 거부하는 것도 여기 포함한다 — 서버가 받지 않는 형식이다.
  검색 토큰 잔량 조회(`available-token`)는 명령으로 노출하지 않는다.
  판정에 쓸 수 없다는 것이 실측으로 확인됐다.
